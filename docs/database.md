# Database

Design notes for the Football Team Organizer PostgreSQL schema (Supabase).

The **authoritative schema source** is `supabase/migrations/`. This document
explains the design — not the SQL. Read it alongside the migration files; do not
duplicate column definitions here.

---

## Core entities

```
clubs
 └── managers        (club-level management staff)
 └── coaches         (club-level coaching staff)
 └── players         (club-level player registry)
 └── guardians       (club-level guardian registry)
 └── venues          (club-level places)
 └── teams
      └── team_coaches        (coach ↔ team assignment)
      └── team_players        (player ↔ team squad membership)
      └── team_members        (auth user ↔ team role)
      └── competitions
      └── matches
           └── match_players   (match-day availability)
           └── match_periods
                └── match_period_starters
           └── goals
           └── cards
      └── player_of_the_month

people   (central identity — linked by person_id to managers/coaches/players/guardians)
 └── player_contacts          (sensitive contact details, stricter RLS)
 └── player_guardians         (guardian ↔ player links)
 └── person_invitations       (invite tokens)
 └── player_development_objectives
 └── coach_development_objectives
```

All tables have a `uuid` primary key generated by `gen_random_uuid()`.

## Key relationships

### People and roles

`people` is the central identity table — it stores name, email, phone, and
Auth link (`auth_user_id`). Domain roles (`managers`, `coaches`, `players`,
`guardians`) each have a `person_id` FK to `people`. A single person can hold
multiple roles (e.g. be both a coach and a guardian). This avoids duplicating
personal details across role tables.

`team_members` stores the auth-user-to-team binding for access control. It is
separate from the domain role tables. A coach must have both a `coaches` /
`team_coaches` row (for their staff profile) **and** a `team_members` row
(for write access). One person can hold multiple `team_members` rows on the same
team (one per role).

### Club → team → everything else

`clubs` is the top-level tenant. Every team belongs to one club. Squad, matches,
competitions, and goals all carry a `team_id`. Players and coaches are
club-level (`club_id`) and assigned to teams via junction tables.

### Match scoring

There are **no** `goals_for` / `goals_against` columns on `matches`. The
aggregate score is derived from `goals` rows (our goals where
`opposition = false` and `own_goal = false`, minus own goals; opposition goals
via `opposition = true`). This keeps the source of truth in goal events.

### Sensitive player data

Personal contact details (`phone`, `email`, `address`, `medical_notes`) live in
`player_contacts` (1:1 with `players`), not on the `players` row itself. This
allows stricter RLS: only management, the player's coaches, the player's
guardians, and the player themselves can read a `player_contacts` row. The
broader `players` table is readable by anyone in the club.

## Migration strategy

All schema changes go through versioned migration files in `supabase/migrations/`.
File names are timestamped: `YYYYMMDDHHMMSS_description.sql`.

- **Never edit an existing migration** that has been applied to any environment.
  Write a new migration instead.
- Migrations are applied in filename order by `npx supabase db push` and by
  `npx supabase start` locally.
- The baseline file (`20260825000000_schema.sql`) is a squash of the original
  migration chain. Subsequent files are incremental.
- After every schema change, regenerate the TypeScript types:
  ```bash
  npx supabase gen types typescript --linked > src/lib/supabase/database.types.ts
  ```
  Commit the updated types with the migration.

## RLS strategy

Row Level Security is enabled on every table. No table is left unprotected.

### Design rules

1. **Policies never reference another RLS-protected table directly.** A policy
   expression runs as the calling user, so joining into another protected table
   causes recursive RLS evaluation. All cross-table checks go through SECURITY
   DEFINER helper functions.

2. **The `*_row` helpers accept column values as arguments** (e.g.
   `can_read_player_row(club_id, user_id)`). This makes `INSERT … RETURNING`
   work — the new row is not yet visible to a self-lookup at insert time.

3. **Helper functions are SECURITY DEFINER** so they execute with elevated
   privileges. Keep their bodies simple; avoid calling other SECURITY DEFINER
   helpers recursively.

4. **The service role bypasses RLS.** Only server-side code that needs to act on
   behalf of the system (invite flows, onboarding) uses the service role client.

### Key helpers

| Function                             | Purpose                                                               |
| ------------------------------------ | --------------------------------------------------------------------- |
| `has_app_access(uuid)`               | Gate for middleware: person linked, status invited/active, has a role |
| `is_club_management(club_id)`        | Caller is a manager of this club                                      |
| `is_club_staff(club_id)`             | Caller is a manager or coach in this club                             |
| `can_read_club(club_id)`             | Caller is any member of this club                                     |
| `can_read_team(team_id)`             | Caller is any member of this team                                     |
| `can_edit_team(team_id)`             | Caller is a coach or management on this team                          |
| `can_edit_match_day(team_id)`        | Caller is a coach, management, or guardian assistant                  |
| `can_view_player_contact(player_id)` | Management, player's coaches, player's guardians, or the player       |
| `can_edit_player(player_id)`         | Management or the player's coaches                                    |

## Roles and permissions

Roles are stored in `team_members` (one row per `(team, user, role)`). A user
may hold multiple roles on the same team.

| Role               | Where stored                                      | Write scope           |
| ------------------ | ------------------------------------------------- | --------------------- |
| Management (club)  | `managers.person_id` linked to `auth_user_id`     | Full club             |
| Management (team)  | `team_members.role = management`                  | That team             |
| Coach              | `team_members.role = coach` (+ `coaches` profile) | Own teams             |
| Guardian assistant | `team_members.role = guardian_assistant`          | Match-day data        |
| Guardian           | `guardians` + `team_members.role = guardian`      | Linked player contact |
| Player             | `players` + `team_members.role = player`          | Own contact           |

Coach write access and RLS helpers key off `team_members.role = 'coach'`, not
the `coaches` profile table alone. A `coaches` row without a matching
`team_members` row grants no write access.

Full permission tables: [`docs/roles.md`](roles.md).

## Seed and test data

`supabase/seed.sql` creates:

- One club (MGA Academy)
- One team (with age group, gender, season label)
- Club manager **John Hall** (`people.id` = `b0000000-0000-4000-8000-000000000001`)
  with `account_status = 'none'` and no `auth_user_id`

The seed does **not** create Auth users or `team_members` rows. After seeding,
manually link an Auth user to John Hall (see [Development](development.md)).

For automated tests, Vitest mocks the Supabase client — the test suite does not
connect to a live database.

## Backup and restore

Daily logical backups run via GitHub Actions (`.github/workflows/db-backup.yml`)
and are stored in S3. The dump contains `roles.sql`, `schema.sql`, and
`data.sql`.

Full backup setup and restore procedure: [Operations](operations.md).
